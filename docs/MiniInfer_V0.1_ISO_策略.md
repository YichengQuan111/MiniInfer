# MiniInfer：v0.1 实施策略与 V1 / V2 升级边界

日期：2026-10-10。I-S-O 阶段：S（策略）。本文是待实施方案，接口、检查点和测试均为计划，不代表已实现或已通过验收。

依据：[v0.1 开发规范](<../MiniInfer 项目说明与 AI Agent 开发规范.md>)、[I 阶段洞察](MiniInfer_V0.1_ISO_洞察.md)、[V1 / V2 求职改进策略](MiniInfer_V1_V2_求职改进策略.md)。原规范规定 v0.1 的必达范围；本文把实现决策具体化，后续版本职责沿用 V1 / V2 策略。

## 1. 主策略与版本职责

**先完成固定 CPU 推理的正确性与资源管理，再加入有界并发，最后用实测证据交付；通过明确的任务、执行和完成边界支持后续升级。**

| 版本 | 主交付 | 进入下一阶段的条件 |
|---|---|---|
| v0.1 | 自写标量 FP32 MLP、所有权、线程池、错误与关闭语义、CPU 测量 | 核心测试、ASan / UBSan、真实基准和复现文档完整；TSan 运行或记录实际限制 |
| V1 | 一个真实视觉模型的 C++ 部署：Python 参考 → ONNX → ORT CPU → TensorRT GPU，同步 FP32 / FP16 对照 | 前后处理与原始输出对齐，任务结果可解释，GPU 结果就绪与资源释放正确，同步部署基线完整 |
| V2 | 有限 GPU 并发、资源复用、Nsight 分析、CUDA 算子实践与一次优化实验 | 生命周期与并发回归通过；同条件前后数据、瓶颈依据和局限可复现 |

V1 保留现有文档中的轻量检测模型候选；模型、导出格式和依赖版本在 V1 实施时核验。v0.1 不安装或实现 ORT、TensorRT、CUDA，也不增加通用图解析。后续升级允许新增模型契约和必要适配，不承诺固定 MLP 接口可以原样支持所有模型。

## 3. 模块边界：现在实现什么，以后复用什么

```text
CLI / Bench
    → InferenceRuntime（v0.1 的 MLP 调用门面）
        → ThreadPool（有界队列、任务、稳定 Worker ID、生命周期）
        → CpuExecutor（固定 MLP 计算）
            → 只读 MlpModel + 对应 Worker 的 Workspace
```

| 模块 | v0.1 设计 | V1 / V2 升级方式 |
|---|---|---|
| 输入 / 结果 | 明确命名或文档标识为 MLP 数据；拥有输入、logits、labels | 视觉任务新增自己的输入、检测结果和预处理契约；不把 64 维接口改称通用接口 |
| Model | 只读 `MlpModel`，固定权重形状与布局 | ONNX / TensorRT 模型工件、引擎和元数据独立管理；MLP 留作回归样例 |
| Buffer / TensorView | CPU 存储与主机可访问视图，所有权和借用寿命分开 | 增加独立设备 Buffer；不把设备地址塞进可解引用的 CPU View |
| CpuExecutor | 接收模型、输入和 Workspace，完成计算；不管理线程、排队或计时报告 | V1 增加执行适配与前后处理；出现第二种真实执行路径后再提取共用接口 |
| ThreadPool | 执行拥有数据的可移动任务；任务获得稳定 Worker ID；不包含 64/128/10、算子或模型类型 | 复用入队、拒绝、异常和关闭机制；GPU 调度按资源与完成语义调整 |
| Worker 资源 | Runtime 持有按 Worker ID 索引的独立 Workspace，在线程启动前准备 | V2 增加执行上下文、设备缓冲、Stream / Event；GPU 槽位与 CPU Worker 数分别配置 |
| 指标 | 请求 ID、结果状态、主机时间点和固定统计口径 | 扩展前处理、H2D、计算、D2H、后处理及 CUDA Event 计时；旧指标语义保持可追溯 |

v0.1 不增加空的 GPU 类、后端注册器、插件接口或通用 Tensor 系统。CMake 只构建 CPU 核心和实际存在的程序。V1 再按需要增加可选依赖目标，保留 CPU 核心及 MLP 回归测试可独立构建。

## 4. 在实现前确定的接口决策

以下为本策略选定的初始方案；若实际验证需要修改，应同时更新契约和受影响的测试。

| 项目 | 初始决策 |
|---|---|
| 数值与布局 | FP32、连续行主序；W1 `[128,64]`、W2 `[10,128]`；输入已经完成 `pixel / 16.0`，CLI 不重复归一化 |
| Batch | 配置增加 `max_batch_size`，初始默认 256，支持 `1 ≤ B ≤ max_batch_size`；形状乘法、字节换算、元素数量和分配尺寸均检查 |
| Workspace | 每 Worker 预留最大 Batch 所需隐藏层缓冲，ReLU 原地处理；logits 和 labels 由 Result 拥有，不能引用随后会复用的 Workspace |
| 基础配置 | `worker_count=1`、`queue_capacity=64`；均须大于零，容量和内存计算须验证；更大 Batch 属于显式配置，不保证其性能收益 |
| 队列容量 | 只计等待任务；执行中的任务不占等待队列容量。调用者持有的输入、future 和结果也须纳入内存分析 |
| 拒绝行为 | 输入非法、队列满、已关闭在调用时立即抛出有上下文的异常；不返回伪造结果；已经接受的任务执行异常由对应 future 传播 |
| 同步 API | 最终 `run(Input input)` 采用 `submit(std::move(input)).get()`：与异步共享接收、排队、关闭和完成语义；传左值会复制，传右值可移动 |
| 同步基线 | D6–D8 直接调用 CpuExecutor 与独立 Workspace 建立计算基线。报告区分直接执行与 Runtime 的排队路径，不把两者都称为相同的单线程模式 |
| 线程安全 | 允许多个外部调用者并发 run / submit / shutdown；调用者负责 Runtime 对象本身的寿命。Worker 不回调同一池的阻塞 run 或 shutdown |
| 关闭 | `Running → Draining → Stopped`；接收判断与入队在同一锁下完成；关闭先停止接收、通知 Worker，再在队列锁外 join；多个 shutdown 调用序列化，返回时均已停止 |
| 构造与析构 | Worker 资源先准备再启动线程；部分启动失败时回收已启动线程。析构执行安全关闭，所有任务与线程结束后才销毁 Model / Workspace |
| argmax 与容差 | 并列取最小索引；初始比较 `abs(a-b) ≤ 1e-4 + 1e-4 × abs(b)`，结合实测误差与类别检查；不任意放宽容差 |

这套同步 API 会包含入队成本与可能的 QueueFull，README 必须明确。其收益是只维护一套接收和关闭协议；直接执行器仍可独立测试与测量。v0.1 中任务完成意味着拥有的 CPU 输出已可用；V1 / V2 必须延续“结果可用后才完成 future”的含义，不能在 GPU 提交后立即报告成功。

## 5. 实施顺序与验收关卡

沿用原文档 15 个工作单元，不强制对应连续日历日期。原估算约 22.5–30 小时；环境与故障处理可能增加时间，每项完成以证据为准。

| D3 | Buffer 与对应测试 | 创建、移动构造/赋值、空状态和安全大小计算有证据，所有权唯一 |
| D4 | TensorView、MlpModel、加载测试 | 固定形状与只读性明确；缺失、过短、过长文件和尺寸错误均拒绝 |

| D7 | 输入/尺寸/异常路径、安全检查与说明 | ASan / UBSan 实际运行；记录命令与结果；同步推理没有已知生命周期错误 |

| D10 | ThreadPool、Runtime、Worker Workspace、run / submit | 至少一条异步路径可用；Input / Result 拥有数据；基本异常交付、drain 和析构 join 已成立 |
| D11 | 多生产者、1/2/4 Worker 正确性与压力测试 | 与同步基线一致，无串扰；每个已接受请求完成一次，成功与失败均可回收 |

## 6. 数据与测试策略

D1 导出小份真实权重与固定参考样本，并记录训练参数、Python / NumPy / scikit-learn 版本、样本顺序、实际指标和文件 SHA-256。参考计算使用导出的 FP32 数据。小工件进入 Git，额外实验与临时生成目录忽略；复现者运行 C++ 测试时无需重新训练。跨版本重新生成的工件可能存在差异，应保留原工件身份与生成环境。

测试分两层：手算的小型确定性算子用例定位数学和布局错误；真实工件验证加载与完整网络。重复参考样本可以覆盖较大 Batch，但不能表述为新增独立评测样本。训练不作为 Runtime 开发的前置长任务；遇到阻塞先用确定性数据推进基础功能，真实模型仍须在 v0.1 最终验收前补齐。

并发用例通过 promise / condition_variable 等明确条件控制：先占住执行位置，再填满等待队列，验证立即拒绝；提交后改变调用者原始输入，验证任务拥有数据；让测试任务失败，检查 future 异常与后续正常请求；在已知任务状态下关闭，检查接受边界、drain 和线程回收。禁止用 sleep 猜测队列已满或线程已退出。

## 7. 性能测量先定义口径，再采集

| 项目 | 计划口径 |
|---|---|
| 模式 | `direct_cpu` 用于计算基线；`runtime` 用于完整队列路径。Runtime 内比较 1/2/4 Worker，单独说明直接执行与排队执行的差异 |
| 主负载 | 固定输入序列、队列 64、相同在途窗口与采集策略；Batch=1 为主，8/32 做计算负载对照；窗口有上限，不积累无限 future / Result |
| 次数 | 预热 200 次、正式至少 1000 次、重复至少 3 次作为起点；不稳定时增加次数并记录，预热不混入正式统计 |
| 时间点 | 调用前、接收入队、开始执行、执行完成、调用者取得结果；记录主机 steady_clock 时间点 |
| 延迟 | 排队=开始执行−入队；执行=执行完成−开始执行；端到端=取得结果−调用前。采用固定窗口并检查就绪 future，另报告执行完成耗时以识别采集开销；百分位采用排序后最近秩法，索引 `ceil(p×N)-1` |
| 吞吐与结果状态 | 成功完成数 / 正式墙钟时长，单位 req/s；尝试、接受、成功、任务失败、拒绝单独计数。正式测量包含本轮已接受任务的回收，drain 后核验接受数=成功数+失败数；拒绝请求不计成功吞吐，请求数与样本数分别标注 |
| 内存 | 每个配置独立进程运行，记录稳态 RSS 和峰值 RSS 的采集方法、采集范围，以及权重、Workspace、队列与输出占用；若峰值包含准备/预热阶段要明确标注。记录调用者保留结果的策略，不把 Buffer 容量当全部进程内存 |
| 分配 | 计数构建说明覆盖的热路径分配/扩容事件及未覆盖来源；不把局部事件计数宣称为全进程 malloc 次数。正式计时独立运行 |
| 对照条件 | 同硬件、编译器/选项、模型工件、Batch、在途窗口、负载与测量流程；记录系统、供电、后台负载及实际参数 |

原始测量输出保留为机器可读文件，`docs/benchmark.md` 记录配置、结果与解释。基本拒绝计数属于 P0；额外到达率扫描、详细背压曲线和更大计算负载属于 P1，不扩大首版范围。

## 8. V1 / V2 的升级路线与复用边界

| 升级 | 沿用的工程基础 | 必须新增或调整的部分 | 升级验收重点 |
|---|---|---|---|
| v0.1 → V1 | 构建/测试流程、错误分类、测量方法；固定 MLP 回归 | 视觉输入与结果、图像前后处理、模型工件、ORT / TensorRT 执行适配、设备资源 RAII | 先对齐预处理和原始输出，再判断检测结果；GPU 完成后交付结果；同步 FP32 / FP16 对照 |
| V1 → V2 | 已对齐的真实模型、同步部署基线、适合复用的队列与状态协议 | 独立执行上下文和可写缓冲、GPU 槽位、Stream / Event、设备计时、资源复用与调度适配 | 每条执行路径资源隔离；关闭等待设备工作完成；Profile 驱动 CUDA 实践与一个优化实验 |

V1 默认一个模型、固定形状、Batch=1，先同步部署。v0.1 多 Worker 的结果不能证明 TensorRT 对象共享安全；模型引擎与上下文的共享方式要按实际版本验证。V2 再控制 GPU 同时在执行的数量，CPU Worker 数不直接等于 GPU 并发数。

V2 的主机执行完成、GPU 工作完成、输出回到可访问内存是不同事件。future 必须在约定的结果就绪点完成；shutdown 必须等设备工作安全结束，才销毁它依赖的资源。GPU 时长用设备计时，端到端仍用主机计时，两个口径不能互换。

原主规范第 7.2 节的 CUDA V1/V2/V3 是算子学习阶段；求职策略中的产品 V1/V2 是部署与系统工程版本。实施采用后者作为版本主线，自写 CUDA ReLU / Linear 可保留为独立学习实验，避免同名阶段造成范围混淆。控制混合负载、INT8、较大 GEMM 等分支留到核心版本验收后按需要选择。

## 9. 范围收缩与 O 阶段入口
