## 3. V1：实际模型的 C++ 部署闭环

### 3.1 范围与模型

选择一个公开预训练轻量目标检测模型，建议先用 YOLO11n，固定 640×640、Batch=1。它具有公开权重与导出支持，能提供卷积网络、图像预处理和检测后处理的部署练习。具体依赖、导出选项与模型输出格式在实施时验证并固定。[模型文档](https://docs.ultralytics.com/models/yolo11/)、[导出文档](https://docs.ultralytics.com/modes/export/)

Python 用于模型导出、参考输出和评测；C++ 负责推理调用、前后处理、错误处理与测量。使用 ONNX Runtime CPU 建立参考路径，然后接入 TensorRT GPU 的 FP32 / FP16 路径。固定形状和单请求同步执行先通过验收，再进入 V2。ONNX Runtime 提供正式 C++ API。[ORT C++ 文档](https://onnxruntime.ai/docs/get-started/with-cpp.html)

如果检测模型前后处理阻塞过久，可先用一个预训练轻量分类模型缩小范围。此时交付应准确标为分类部署，检测能力仍列为未完成；不要同时维持两个新模型的完整开发任务。

### 3.2 必达任务

| 顺序 | 任务 | 验收证据 |
|---|---|---|
| 1 | 验证 Linux 或 WSL2 GPU 开发链；记录依赖版本 | 最小 C++ / CUDA / 引擎样例可运行，版本与环境记录完整 |
| 2 | 固定模型、ONNX、输入布局、颜色顺序、缩放及输出契约 | 模型与导出配置可追溯；固定参考输入、预处理张量和原始输出 |
| 3 | 实现 ORT C++ 路径及图像前后处理 | 与 Python 对照；覆盖原始张量、输出解析和坐标还原 |
| 4 | 实现 TensorRT C++ 同步推理 | 明确设备缓冲区所有权，执行完成后交付结果；错误有上下文 |
| 5 | 对照 FP32 / FP16 数值与任务结果 | 同一固定数据集上记录误差、检测匹配和 mAP 差异 |
| 6 | 建立部署基线及故障记录 | 分阶段耗时、整体耗时、显存；至少一个实际问题的定位与修复 |

### 3.3 质量标准

- 固定带标注的评测子集及样本清单；子集结果不表述为完整数据集指标。
- 先对齐预处理张量和原始模型输出，再判断检测框差异。对置信度或 NMS 阈值附近的样本单独分析，不能仅要求结果逐位一致。
- 数值容差应依据精度与实测计算差异确定并记录；任务指标允许的差异也需明确。不能通过任意放宽容差掩盖布局或解析错误。
- 覆盖缺失或损坏模型、错误输入、无效形状和推理失败等错误路径。
- CPU、GPU、不同精度的结果分别标注。跨硬件比较用于说明部署选项；同一 GPU 上的前后对照用于判断具体优化效果。
- 固定权重、模型版本、依赖和命令，可在相近环境复现。

V1 的完成标准：他人能按文档执行同一模型；能解释输入输出与精度差异；能展示 C++ 部署代码、实测基线和一次问题定位。

### 3.4 范围边界

初次交付集中在一个模型和固定形状。INT8、动态形状、TensorRT Plugin、多模型调度等按目标岗位再加入后续专题。训练新模型、RL / VLA 复现和完整机器人平台不进入 V1 验收。

## 4. V2：GPU 推理性能与资源管理

### 4.1 必达任务

| 顺序 | 任务 | 验收证据 |
|---|---|---|
| 1 | GPU 内存、Stream / Event、执行上下文的 RAII 与生命周期 | 正常结束、异常、关闭后均无已知资源问题；结果完成语义清晰 |
| 2 | 有限并发与缓冲区复用 | 同时执行的任务不共享可写输入、输出或不安全的执行上下文；并发上限明确 |
| 3 | 分离主机计时与 GPU 计时 | 排队、预处理、传输、计算、后处理和整体延迟的口径一致 |
| 4 | Nsight Systems 分析真实管道 | 可指出等待、同步、拷贝或计算瓶颈，并保存报告与判断依据 |
| 5 | 完成一个基础 CUDA 算子实践 | 优先做归一化与 HWC→NCHW 的融合预处理；有 CPU 差分验证和性能对照 |
| 6 | 根据 Profile 完成至少一个系统优化实验 | 相同条件下的前后数据、正确性回归和失败/局限分析 |
| 7 | 验证不同到达负载与并发配置 | 吞吐、P50/P95/P99、队列时长、拒绝率、内存/显存及结果正确性 |

具体优化候选包括预分配、减少复制、Pinned Memory、流水线重叠或预处理融合。选择由 Profile 决定，不要求全部实现，也不要求结果一定加速。

CUDA 算子是独立能力验收：能解释线程映射、布局和访存，正确运行并测量。只有在证据支持时才保留到主推理路径；如果传输或启动成本让整体更慢，应报告并解释。

TensorRT 的引擎性能与应用整体性能需分别报告，检查基准是否包含 H2D / D2H、CUDA Graph 和同步成本。以当前实际安装版本的行为和参数为准。[TensorRT 性能测量文档](https://docs.nvidia.com/deeplearning/tensorrt/11.4.0/performance/benchmarking.html)

### 4.2 并发与测量约束

- 每条同时执行的推理路径有独立的可写资源；执行上下文和引擎对象的共享按实际 API 线程安全约定处理。
- Worker 完成 CPU 提交不等于 GPU 完成；future 交付结果前，应满足对应的数据就绪与所有权契约。
- 关闭 Runtime 时，等待已提交 GPU 工作完成后再释放其使用的资源。
- 使用有限的 GPU 并发槽位与缓冲区。CPU Worker 数与 GPU 并发数分别配置和测量。
- 区分低延迟 Batch=1 与批量吞吐实验。排队、拒绝及超期请求均单独计数，不用增加 Batch 掩盖单请求延迟。
- 记录笔记本供电、运行状态和温度等条件，减少后台 GPU 负载；不把本机测量外推为 Orin 或生产平台性能。
- 队列容量上限限制积压数量；超期策略处理迟到结果；P99 是测量值。这些均不构成硬实时保证。

V2 的完成标准：解释真实瓶颈，展示 GPU 生命周期与并发安全，提供 CUDA 实践和一次完整优化实验，并能复现测量结果。

## 5. 控制背景的差异化展示

V2 核心验收通过后，可增加小型“控制任务与 AI 推理混合负载”实验，复用一个已有 MPC 或 PID 案例。只选已有、可运行的案例；先验证控制基线，再叠加推理负载。

实验包含三个工况：控制任务独立运行；控制与推理共同运行；应用一种资源或调度改进后共同运行。控制任务、推理样本和负载参数保持可追溯。

优先报告控制周期耗时、抖动、超期率以及推理结果年龄。若已有仿真支持延迟注入，再报告跟踪误差或约束违反情况。普通并发性能实验不能自动称为感知控制闭环、实车或硬实时验证。

推理请求可以携带时间戳和时间预算，明确队列中已过期任务及迟到结果的处理。已经提交的 GPU 工作不假定可以立即抢占；过期结果标记并按约定丢弃，资源回收仍等待安全时机。

这一展示用于说明你理解控制应用中的时间与资源约束。神经控制器训练、MPC 蒸馏、RL / VLA 等属于新的算法任务，应在岗位明确需要时另行评估。

## 6. AI Infra 补强的分支

V2 的系统实验与 CUDA 基础完成后，按具体 JD 只增加一个专题：

| 目标岗位 | 可选专题 | 新增证据 |
|---|---|---|
| GPU 算子 / 高性能计算 | 较大 GEMM：基础实现、分块实现、cuBLAS 对照 | 正确性、访存与计算瓶颈、不同矩阵形状的性能分析 |
| 端侧部署 / 压缩 | INT8 PTQ | 校准与评测样本分离，精度—性能—显存对照 |
| LLM 推理执行 | 在实际框架中定位一个 KV Cache / 批调度 / 内存问题 | 框架源码或配置证据、可复现负载、改动与测试 |

这些专题不同时纳入 V2 必达项。已有两个版本主要支持部署与推理执行方向；GPU 算子深度岗、LLM 核心优化岗或 Kubernetes 算力平台岗仍需要各自的专项证据。公开 NVIDIA 算子库实习将 CUDA、框架和性能分析列为基础，并将引擎、编译器及开源贡献列为优先经历。[NVIDIA 岗位](https://nvidia.wd5.myworkdayjobs.com/en-US/NVIDIAExternalCareerSite/job/Software-Engineer-Intern--AI-and-DL-Kernel-Libraries---2027_JR2026307)
