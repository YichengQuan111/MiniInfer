## 3. V1：实际模型的 C++ 网络推理服务

### 3.1 范围与模型

选择一个公开预训练轻量目标检测模型，建议先用 YOLO11n，固定 640×640、Batch=1。它具有公开权重与导出支持，能提供卷积网络、图像预处理和检测后处理的部署练习。具体依赖、导出选项与模型输出格式在实施时验证并固定。[模型文档](https://docs.ultralytics.com/models/yolo11/)、[导出文档](https://docs.ultralytics.com/modes/export/)

Python 用于模型导出、参考输出和评测；C++ 负责推理调用、前后处理、错误处理与测量。使用 ONNX Runtime CPU 建立参考路径，然后接入 TensorRT GPU 的 FP32 / FP16 路径。固定形状和单请求同步执行先通过验收，再接入 D16 的 TCP 服务。ONNX Runtime 提供正式 C++ API。[ORT C++ 文档](https://onnxruntime.ai/docs/get-started/with-cpp.html)

V1 延续固定数量的连接处理线程与有限任务队列，GPU 执行槽位先固定为 1。连接线程负责收发与结果等待，执行线程独占模型执行上下文和可写资源；连接数增加不自动增加 GPU 并发。启动参数选择 ORT CPU、TensorRT FP32 或 FP16，暂不做请求级后端切换。

如果检测模型前后处理阻塞过久，可先用一个预训练轻量分类模型缩小范围。此时交付应准确标为分类部署，检测能力仍列为未完成；不要同时维持两个新模型的完整开发任务。

### 3.2 必达任务

| 顺序 | 任务 | 验收证据 |
|---|---|---|
| 1 | 验证 Linux 或 WSL2 GPU 开发链；记录依赖版本 | 最小 C++ / CUDA / 引擎样例可运行，版本与环境记录完整 |
| 2 | 固定模型、ONNX、输入布局、颜色顺序、缩放及输出契约 | 模型与导出配置可追溯；固定参考输入、预处理张量和原始输出 |
| 3 | 实现 ORT C++ 路径及图像前后处理 | 与 Python 对照；覆盖原始张量、输出解析和坐标还原 |
| 4 | 实现 TensorRT C++ 同步推理 | 明确设备缓冲区所有权，执行完成后交付结果；错误有上下文 |
| 5 | 对照 FP32 / FP16 数值与任务结果 | 同一固定数据集上记录误差、检测匹配和 mAP 差异 |
| 6 | 定义视觉消息类型，接入 TCP 服务与 C++ 客户端 | 同一参考图像的本地/远程预处理、输出和错误分类一致；协议版本及长度上限有测试 |
| 7 | 验证多连接、有限排队和完整服务关闭 | 计算槽位为 1 时结果仍正确；BUSY、慢客户端、断连及推理失败后恢复；所有线程与 GPU 资源回收 |
| 8 | 建立本地部署与网络服务两套基线 | 分阶段耗时、客户端整体耗时、拒绝/超时、内存/显存；至少一个实际问题的定位与修复 |

### 3.3 质量标准

- 固定带标注的评测子集及样本清单；子集结果不表述为完整数据集指标。
- 先对齐预处理张量和原始模型输出，再判断检测框差异。对置信度或 NMS 阈值附近的样本单独分析，不能仅要求结果逐位一致。
- 数值容差应依据精度与实测计算差异确定并记录；任务指标允许的差异也需明确。不能通过任意放宽容差掩盖布局或解析错误。
- 覆盖缺失或损坏模型、错误输入、无效形状和推理失败等错误路径。
- 保留 D16 的协议、收发、连接上限与关闭回归；新增错误视觉格式、尺寸/长度不符、超大图像及响应上限测试。
- 同一执行配置下，网络路径与本地路径采用同一前后处理与结果契约；GPU 结果回到可用主机内存后才编码回包。
- CPU、GPU、不同精度的结果分别标注。跨硬件比较用于说明部署选项；同一 GPU 上的前后对照用于判断具体优化效果。
- 固定权重、模型版本、依赖和命令，可在相近环境复现。

V1 的完成标准：他人能分别通过本地 CLI 和 TCP 客户端运行同一模型；能解释输入输出、精度差异、错误和关闭行为；能展示 C++ 服务代码、两套实测基线和一次问题定位。只完成引擎调用时标记为本地部署子项完成，不提前宣称服务验收通过。

### 3.4 视觉协议与服务边界

沿用 D16 的帧头、request_id 和错误响应，新增视觉请求类型及对应响应；已定义的 MLP 布局保持原义，未知类型明确拒绝。修改已有字段或语义时提升协议版本。协议版本与项目 V1/V2 版本分别记录。

初版采用原始 RGB8、连续 HWC 图像：请求携带宽、高、格式和精确字节数，客户端解码图片，服务端执行固定的 resize / letterbox、归一化和布局转换。模型输入固定 640×640、Batch=1，原图大小仍可不同；像素数、宽高和总帧长度各有配置上限，在分配和乘法运算前校验。需要 JPEG / PNG 传输时再增加独立消息类型和解码限制，不同时维护两套首版输入。

检测响应明确类别、置信度、原图坐标及框数量上限；坐标还原和 NMS 规则与本地路径一致。每连接仍只有一个在处理的请求，服务只接收图像内容，不接收服务器文件路径或模型上传。若降级为分类模型，定义独立分类结果类型并如实调整验收。

V1 的视觉帧与响应上限按新数据契约重新设置，不能直接沿用 D16 的 65540 字节 MLP 消息体上限，也不能为支持图像取消上限。图像传输方案、颜色顺序、最大检测数在实现协议前写入测试样例。

### 3.5 范围收缩

初次交付集中在一个模型、固定形状、单 GPU 槽位和 D16 的连接线程方案。epoll 放到 V2；INT8、动态形状、TensorRT Plugin、多模型调度、HTTP/gRPC、鉴权和公网部署均不进入 V1 必达范围。检测链路受阻时先缩为分类任务；GPU 环境受阻时保留 ORT 网络服务检查点，TensorRT 子项继续标为未完成。训练新模型、RL / VLA 复现和完整机器人平台不进入本轮验收。

## 4. V2：事件驱动网络与 GPU 性能工程

V2 分两步演进：先在固定 GPU 槽位为 1 时完成 epoll 网络回归，再扩展 GPU 并发与资源复用，最后测量和优化。网络模型与 GPU 并发不要在同一次改动中同时更换，以便确定错误与性能变化的来源。

### 4.1 必达任务

| 顺序 | 任务 | 验收证据 |
|---|---|---|
| 1 | 单 I/O 线程的非阻塞 epoll LT 事件循环，复用已有协议 | 分片收发、EAGAIN、半关闭、慢连接、超时及连接关闭后 fd 复用测试通过 |
| 2 | 有界完成队列与 eventfd 通知，连接状态和结果寿命分离 | I/O 线程不等待推理 future / GPU；已断连请求的迟到结果安全回收，不写入复用后的 fd |
| 3 | GPU 内存、Stream / Event、执行上下文的 RAII；有限执行槽位与缓冲复用 | 同时执行的路径不共享可写资源或不安全上下文；关闭等实际设备工作完成 |
| 4 | 全链路背压与异常关闭 | 连接、收包、等待执行、完成结果、发包均有上限；慢读、过载、超时及关闭竞争无泄漏或死锁 |
| 5 | 分离客户端、本地 CPU 与 GPU 计时，分析真实管道 | 网络端到端、收发、排队、前后处理、H2D / D2H、设备计算口径清楚；保存 Nsight Systems 报告 |
| 6 | 完成一个基础 CUDA 算子实践 | 优先做归一化与 HWC→NCHW 融合预处理；有 CPU 差分验证和性能对照 |
| 7 | 根据 Profile 完成至少一个系统优化实验 | 同条件前后数据、正确性回归和失败/局限分析；不以必须加速作为验收条件 |
| 8 | 验证到达率、连接数与 GPU 槽位配置 | 吞吐、P50/P95/P99、拒绝率、超时、队列高水位、内存/显存及正确性完整 |

具体优化候选包括预分配、减少复制、Pinned Memory、流水线重叠或预处理融合。选择由 Profile 决定，不要求全部实现，也不要求结果一定加速。

CUDA 算子是独立能力验收：能解释线程映射、布局和访存，正确运行并测量。只有在证据支持时才保留到主推理路径；如果传输或启动成本让整体更慢，应报告并解释。

TensorRT 的引擎性能与应用整体性能需分别报告，检查基准是否包含 H2D / D2H、CUDA Graph 和同步成本。以当前实际安装版本的行为和参数为准。[TensorRT 性能测量文档](https://docs.nvidia.com/deeplearning/tensorrt/11.4.0/performance/benchmarking.html)

### 4.2 网络完成通知与资源边界

```text
TCP 客户端 ↔ epoll I/O 线程（帧解析、连接状态、限额、非阻塞发送）
                   ↓ 拥有型请求 + 连接标识/代次 + request_id
                有界执行队列 → 有限 GPU 槽位 → 已就绪的拥有型结果
                   ↑                     ↓
                I/O 线程 ← eventfd 通知 + 有界完成队列
```

采用水平触发 LT 入门，设置每轮每连接处理字节数/帧数预算，防止繁忙连接长时间占用事件循环。有待发数据才关注可写事件；可读/可写只表示可以尝试 I/O，仍要处理短读短写和 `EAGAIN`。epoll 与 eventfd 的接口语义以 Linux 文档为准。[epoll](https://man7.org/linux/man-pages/man7/epoll.7.html)、[eventfd](https://man7.org/linux/man-pages/man2/eventfd.2.html)

现有 `std::future` 不能直接作为 epoll 可监听的 fd。执行层或适配层在结果就绪后发布到完成队列，并写 eventfd 唤醒 I/O 线程；不为每请求新建等待线程，也不在事件循环中阻塞 `future.get()`。通知只是唤醒信号，实际结果与同步由完成队列管理。

连接 fd 及其读写、关闭由 I/O 线程统一管理。任务保存连接标识和代次，不保存可悬空的连接引用；结果返回时检查连接仍存在且代次一致，避免 fd 数值复用后把旧结果发给新客户端。完整请求被接受后才计入任务，连接关闭与任务结束分别记账。

连接数、每连接接收/发送字节数、全局在途请求、执行队列及完成结果队列均有上限。接受执行前预留有界的结果交付名额，名额一直保留到结果发送完成或丢弃；队列消费只转移所有权，不提前释放名额。关闭时 I/O 线程继续消费完成通知，直到执行层排空，再按期限处理剩余发送；不能先停止消费者再等待被完成队列阻塞的生产者。

慢读连接达到发送高水位时暂停接收新业务，超过发送期限则关闭并回收。超时不意味着已提交 GPU 工作可立即取消，设备资源仍在安全完成后释放。多 Reactor、边缘触发 ET、io_uring、连接内多请求流水线和零拷贝不进入首轮 V2 验收。

### 4.3 GPU 并发与测量约束

- 每条同时执行的推理路径有独立的可写资源；执行上下文和引擎对象的共享按实际 API 线程安全约定处理。
- Worker 完成 CPU 提交不等于 GPU 完成；future 交付结果前，应满足对应的数据就绪与所有权契约。
- 关闭 Runtime 时，等待已提交 GPU 工作完成后再释放其使用的资源。
- 使用有限的 GPU 并发槽位与缓冲区。CPU Worker 数与 GPU 并发数分别配置和测量。
- TensorRT 执行上下文按执行槽位隔离；同一上下文不得被并发使用。具体 API、错误行为和共享边界在锁定版本时核验。[TensorRT 线程模型](https://docs.nvidia.com/deeplearning/tensorrt/latest/architecture/how-trt-works.html)
- 区分低延迟 Batch=1 与批量吞吐实验。排队、拒绝及超期请求均单独计数，不用增加 Batch 掩盖单请求延迟。
- 记录笔记本供电、运行状态和温度等条件，减少后台 GPU 负载；不把本机测量外推为 Orin 或生产平台性能。
- 队列容量上限限制积压数量；超期策略处理迟到结果；P99 是测量值。这些均不构成硬实时保证。

基准保留三条路径：V1 的本地执行、V1 的连接线程服务、V2 的 epoll 服务。比较网络模型时固定 GPU 槽位、模型、Batch、输入序列、连接复用和负载；比较 GPU 槽位时固定网络模型。客户端端到端使用客户端自己的单调时钟，不直接减去另一进程或机器的时间戳；建连、预热与正式测量分别记录。

先做固定并发数实验，再做受控到达率实验。记录计划发送与实际发送数量、生成器延迟、成功、拒绝、超时、断连与执行失败；发送器跟不上目标速率时不能宣称系统承受了该速率。服务端计算完成数、发送完成数和客户端成功数分别报告；成功样本的 P99 不能掩盖拒绝或超时。

V2 的完成标准：解释网络、排队与 GPU 中的真实瓶颈；展示事件循环、结果通知、背压及 GPU 生命周期安全；保留 CPU 网络回归，并提供 CUDA 实践和一次完整优化实验。只有网络重构或只有 GPU 优化时，应分别标注已完成子项。

## 5. 控制背景的差异化展示

V2 核心验收通过后，可增加小型“控制任务与 AI 推理混合负载”实验，复用一个已有 MPC 或 PID 案例。只选已有、可运行的案例；先验证控制基线，再叠加推理负载。

实验包含三个工况：控制任务独立运行；控制与推理共同运行；应用一种资源或调度改进后共同运行。控制任务、推理样本和负载参数保持可追溯。

优先报告控制周期耗时、抖动、超期率以及推理结果年龄。若已有仿真支持延迟注入，再报告跟踪误差或约束违反情况。普通并发性能实验不能自动称为感知控制闭环、实车或硬实时验证。

推理请求可以携带时间戳和时间预算，明确队列中已过期任务及迟到结果的处理。已经提交的 GPU 工作不假定可以立即抢占；过期结果标记并按约定丢弃，资源回收仍等待安全时机。

这一展示用于说明你理解控制应用中的时间与资源约束。神经控制器训练、MPC 蒸馏、RL / VLA 等属于新的算法任务，应在岗位明确需要时另行评估。

## 6. AI Infra 补强的分支

V2 的系统实验与 CUDA 基础完成后，按具体 JD 只增加一个专题：

| 目标岗位 | 可选专题 | 新增证据 |
|---|---|---|
| GPU 算子 / 高性能计算 | 较大 GEMM：基础实现、分块实现、cuBLAS 对照 | 正确性、访存与计算瓶颈、不同矩阵形状的性能分析 |
| 端侧部署 / 压缩 | INT8 PTQ | 校准与评测样本分离，精度—性能—显存对照 |
| LLM 推理执行 | 在实际框架中定位一个 KV Cache / 批调度 / 内存问题 | 框架源码或配置证据、可复现负载、改动与测试 |

这些专题不同时纳入 V2 必达项。已有两个版本主要支持部署与推理执行方向；GPU 算子深度岗、LLM 核心优化岗或 Kubernetes 算力平台岗仍需要各自的专项证据。公开 NVIDIA 算子库实习将 CUDA、框架和性能分析列为基础，并将引擎、编译器及开源贡献列为优先经历。[NVIDIA 岗位](https://nvidia.wd5.myworkdayjobs.com/en-US/NVIDIAExternalCareerSite/job/Software-Engineer-Intern--AI-and-DL-Kernel-Libraries---2027_JR2026307)

## 7. 已有项目如何组合

| 经历 | 在作品集中承担的作用 |
|---|---|
| 现有 C++ 项目 | 用实际代码、调试和测试证明工程基础；按既有内容呈现 |

| MPC / PID 经历 | 展示建模、约束、反馈和控制实验；可复用为混合负载案例 |

实验统计和验收由确定性脚本完成；Agent 可以辅助解释和定位，但不生成缺失的实验数据。无需为了统一项目叙事新增聊天界面、RAG 或大模型服务依赖。

简历按每个项目的已验证贡献填写。V1 验收后可以开始投递相关部署 / AI 软件岗位；V2 继续补强 GPU 资源与性能证据。控制背景和硕士学历不能替代未完成的部署实践。

## 8. 工作量与检查点

以下为规划估算，尚无实际开发记录验证。未知投递截止时间，因此按工作量安排，不承诺固定日历日期。

| 范围 | 估算有效工作量 | 检查点 |
|---|---|---|
| D16 | 20–35 小时 | Echo → 协议与截止时间 → 远程 MLP → 有限并发 → 关闭与回归 |
| V1 | 40–60 小时 | ORT 对照 → TensorRT 同步 → 视觉协议与 TCP 服务 → 本地/网络基线 |
| V2 | 55–80 小时 | 单 GPU 槽位下 epoll 回归 → 有限 GPU 并发 → Profile → CUDA/优化与负载实验 |
| 可选控制展示 | 10–15 小时 | 既有控制案例可复现，完成资源干扰对照 |
| 可选 GEMM 专题 | 20–30 小时 | 正确性与性能分析完整；不与控制展示同时扩张 |

D16 / V1 / V2 必达项粗估合计 115–175 小时；按每周 15 小时约为 8–12 周。D1–D15 已完成，不重复计入。网络初学者的学习、调试与工具链兼容可能使实际耗时超出范围；完成 D16.1 / D16.2 后用实际记录修订后续估算，编号不对应日历天。

进度不足时先取消可选控制/GEMM 专题和额外模型；V1 收缩模型任务，V2 限制为单 I/O 线程和少量 GPU 槽位。协议正确性、资源上限、关闭安全和真实测量不能以赶进度为由省略。每次实施一个明确子项，网络改造和 GPU 并发分别验收。

[主规范](<../MiniInfer 项目说明与 AI Agent 开发规范.md>)第 7.2 节与第 15 节使用本路线作为迭代入口；D16 的协议及基础网络验收以 [D16 计划](D16_TCP_网络编程学习扩展.md)为准。后续实施发生契约变化时同步更新计划、代码和受影响的测试，不把待实施表格当作成果记录。
