# MiniInfer：C++ 视觉模型部署与推理性能优化——V1 / V2 计划

初版：2026-10-10；视觉部署与性能主线修订：2026-10-11；V2 完整 GPU 预处理方案修订：2026-10-15。本文按 **I【洞察】→ S【策略】→ O【行动】** 组织，描述版本范围与验收要求；实际完成状态以 [README](../README.md)及对应版本的验收记录为准。**本轮仅更新 V2 计划，新增完整 GPU 预处理方案尚未实施或实测，不计为已有成果。**

用户已确认目前只有现有电脑和 NVIDIA GPU，没有可用端侧开发板。当前交付为**在现有 GPU 上验证的 C++ 视觉推理组件与性能实验**，面向本地应用和单机服务集成；车企、机器人与边缘计算作为重点应用方向。真实 ARM / Jetson / NPU 适配及板端指标另列，不作为 V1 / V2 完成条件。

### 3. 模型选择与性能优化的边界

继续以 **Depth Anything V2 Small（ViT-S）相对深度模型**为唯一主负载，不同时维护第二套新模型。它用于学习视觉 Transformer 的部署与优化；其输出不是可直接用于避障或控制的米制距离。[官方模型仓库](https://github.com/DepthAnything/Depth-Anything-V2)

主线优化覆盖已有 Small 权重下的 FP16、静态输入尺寸选择、前后处理、内存复用与异步执行；选择性 INT8 是独立进阶分支。降低分辨率不改变参数量，较小模型文件也不保证较低峰值显存。每项改动都要有正确性和整体代价对照；剪枝、蒸馏、QAT 和重训练留作后续专题。

历史记录中的 RTX 4080 Laptop GPU / 约 12 GB 显存仅供准备；V1.1 核验实际设备、驱动、WSL2 / Linux 和 CUDA / TensorRT 组合。笔记本资源预算实验不能换算成 Orin 时延、功耗或热稳态表现。

### 4. 完整 GPU 预处理的收益假设与适用条件

现有 [C++ 预处理](../src/depth/preprocess.cpp)在 CPU 上完成 RGB8 转 FP32 / 除以 255、等比双线性缩放、补边、通道归一化及 HWC→NCHW，再由 [TensorRT 执行入口](../src/depth/trt_runner.cpp)上传模型输入。V2.4 增加候选路径：**上传已解码的原始 RGB8 像素，在 GPU 上融合这些像素操作，直接写入 TensorRT 输入缓冲区。** CPU 保留输入校验、几何元数据计算、任务调度和结果后处理；JPEG / PNG / 视频解码不属于这项 CUDA 实作。

优化假设是减少 CPU 像素计算、中间数组与重复读写，并让预处理结果留在显存供模型直接使用。上传量取决于原图尺寸：RGB8 为 `3 × 原图宽 × 原图高` 字节，现有 FP32 模型输入为 `12 × 模型宽 × 模型高` 字节，不能预设前者总是更小。[CUDA 数据传输建议](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#data-transfer-between-host-and-device)

| 输入 / 路径 | 上传内容 | 按尺寸计算的数据量 |
|---|---|---:|
| README 基准图，CPU 预处理后上传 | 518×518×3 个 FP32 数值 | 3,219,888 字节，约 3.07 MiB |
| 同一张 1024×683 图，完整 GPU 预处理 | 原始 RGB8 像素 | 2,098,176 字节，约 2.00 MiB，比上一行少约 35% |
| 1920×1080 输入，完整 GPU 预处理 | 原始 RGB8 像素 | 6,220,800 字节，约 5.93 MiB，高于固定 518 输入的上传量 |

以上仅为字节数推算，**不是耗时实测或加速比**；392 配置须按自身模型尺寸重新计算。原图较大时，额外上传可能抵消 CPU 计算节省；并发时，GPU 预处理还可能与模型争用计算和带宽，而原 CPU 路径可与其他请求的 GPU 推理重叠。因此同时比较单请求延迟、持续请求吞吐、P99 与资源占用，完整 GPU 路径不自动成为默认配置。

### 2. V1 P0 必做：可验证、可集成、可重建的深度部署

#### 2.1 固定模型与输入输出契约

首个基线仍为 Batch=1、RGB、NCHW、模型输入 **`[1,3,518,518]`**。官方默认变换保持纵横比并满足 14 倍数，`input_size=518` 不保证任意图像都成为方形；本项目固定形状包装沿用 **等比 resize + 居中 padding → 归一化 → NCHW**，固定取整、填充值、插值和坐标规则。[官方前后处理](https://github.com/DepthAnything/Depth-Anything-V2/blob/main/depth_anything_v2/dpt.py)

Python 和 C++ 使用同一规范，保存变换元数据、预处理张量及原始输出。后处理去除 padding 并恢复原图尺寸；对外返回拥有型 FP32 相对深度图，明确宽高、布局、字节序、语义版本及近远方向。伪彩色 / 逐图 min-max 仅作显示，不进入数值验收；与官方默认几何处理不同的成绩不能冒充官方评测结果。

固定模型仓库提交、权重 / ONNX 哈希、导出包装、opset、依赖、引擎构建选项与实际精度模式。ONNX / TensorRT 转换需要独立验证，不能把社区导出示例视为项目已完成的兼容性证明。

#### 2.2 C++ 部署 SDK 与后端生命周期

首版提供小而明确的模型初始化、同步推理、配置查询和关闭接口；V2 P0 完善可靠异步提交，实时帧策略按 P1.F 选做。模型包定义输入输出、预处理、后处理、后端与精度配置，调用方不管理裸设备指针或 TensorRT 上下文。只抽取 ORT / TensorRT 已存在的共同职责，不提前设计通用插件注册系统。

执行顺序为 **Python FP32 → ORT C++ CPU FP32 → TensorRT FP32 → TensorRT FP16**。FP32 / FP16 是实验配置，需记录实际图中精度、混合精度及 TF32 设置；不依据开关名称推断全部层的执行精度。初始化 / 引擎加载发生在服务接收业务前，暂不做热更新与请求级后端切换。

GPU 槽位固定为 1，上下文、Stream、缓冲及工作内存由 RAII 管理；多个 SDK / TCP 调用方通过同一有界执行入口串行使用该槽位，不能同时驱动同一上下文。CPU 提交成功不代表结果就绪；只有推理、D2H 和后处理完成，拥有型结果才可交付。ORT CPU 用于参考与显式可选的 CPU 运行，不在 GPU 故障后静默回退并沿用原延迟承诺。

#### 2.3 精度与任务效果验收

| 层次 | 验收内容 | 证据 |
|---|---|---|
| 前后处理 | 颜色、resize / padding、布局、归一化、深度尺寸还原 | 横图 / 竖图、极端像素和边缘样例；中间张量及变换参数 |
| 部署数值 | 相同张量输入的各后端原始输出与还原结果 | MAE / RMSE、最大与 P99 绝对误差、非有限值、`atol + rtol × abs(reference)` 越界比例 |
| 任务保持 | 独立带近远排序标注的小子集 | 固定有效点对、近远方向及不确定点规则，对照各后端排序正确率 / 退化 |

开发 / 调参样本与最终验收样本分开；门槛在最终测试前冻结，FP32 / FP16 分别设置，不用任意放宽容差掩盖错误。原始张量对齐不允许逐图缩放、平移或 min-max。相对深度不直接作为米制 AbsRel / RMSE 测距成绩；无标注图片只能支持部署一致性。最终报告写清子集规模、失败样例和适用范围。

至少形成一份可复现的部署核验 / 排查记录：保存输入、检查项、证据与结论。若出现前处理偏差、导出节点、尺寸 / 布局错误、精度下降或引擎兼容问题，补充定位、修复与回归；若没有故障，可记录验证通过的假设，不为满足验收制造或编造问题。

#### 2.4 本地调用、TCP 与部署包

**本地 SDK / CLI 是主要交付，TCP 是调试、远程调用和工程回归入口。** 复用 D16 固定连接线程和有界队列，不以高连接数或网络重构作为 V1 重点。新增 RGB8 HWC 请求与 FP32 稠密深度响应，保持 MLP 消息原义；请求 / 响应格式改变时按协议契约升级。

图像大小、维度乘法、请求和响应长度、连接数、排队数及在途字节均有上限。深度响应按 `4 × 原图宽 × 原图高 + 元数据` 预算，不能套用 MLP 的 65540 字节上限；接纳时预留结果名额，慢读不能使结果缓冲无界增长。覆盖队列满、非法输入、断连、超时、关闭及资源回收。

部署包至少包含 C++ 接口 / 示例、模型与 ONNX 清单、前后处理配置、引擎构建流程、版本 / 硬件记录、启动参数和黄金回归样例；运行时推理不依赖 Python 服务。固定精度与模型配置，错误信息能区分模型包不匹配、引擎加载失败、输入错误和执行失败。

TensorRT engine 按目标环境生成并缓存，缓存标识包含模型 / 配置 / 精度 / 软件栈 / 目标硬件信息，加载前检查兼容性。默认不把桌面 engine 当作跨架构交付包；转到 ARM / Jetson 时重新构建并验收，可移交的是源码、模型、配置、构建方法与测试证据。[TensorRT engine 兼容性](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/engine-compatibility.html)

V1 基线分别记录离线引擎构建时间、进程启动到可接收请求、首请求、预热后稳态的延迟 / 内存；区分直接模型执行、本地 SDK 全链路及 TCP 客户端端到端。保存 Batch=1 P50 / P95 / P99、吞吐、主机内存 / 显存和失败分类，量化前后处理及传输开销。

### 3. V2 P0 必做：可靠异步与可解释的性能优化

#### 3.1 先建立可比较的负载与性能基线

以固定图像序列按预设时间表提交请求，复用 SDK / CLI；P0 不要求摄像头、视频解码或 ROS2。记录计划与实际提交时刻、生成器滞后、接纳、拒绝、完成和交付，正常负载与持续过载分开测试。吞吐、失败比例与延迟同时报告，不能只统计少量成功请求。

V2.1 根据 V1 实测冻结输入到达率、允许的任务精度退化、延迟目标、队列 / 应用缓冲限额、样本量及测试时长。这些是本机实验目标，不是车企量产指标；P99 不构成硬实时保证。先用 Nsight Systems 找出 CPU 前后处理、复制、GPU 执行、等待和分配的主要开销，再确定优化假设。为 V2.4 单列 RGB8 / FP32 上传字节数、CPU 预处理分段与请求间重叠，选择能覆盖上传量较小和较大情形的代表性原图尺寸。

#### 3.2 精度、静态尺寸与资源成本对照

同一 Small 权重比较 **518×518 与一个较小静态尺寸，默认 392×392**；分别导出 / 构建静态模型，重新核验前后处理及任务效果。先固定尺寸比较 FP32 / FP16，再固定精度比较尺寸，最终复验选定组合。不增加动态 shape 调度，不同时更换模型和多个变量。

三条预处理路径使用对应静态配置的同一几何规则、模型尺寸和输入类型；GPU 输出容量与 engine 绑定一致。当前主线源码仍固定 518，392 的模型、CPU 参考及 GPU 路径适配属于待实施的配置扩展，不能把原图尺寸变化误写成模型支持动态 shape。

每种配置记录任务指标、Batch=1 延迟、端到端 P99、成功吞吐、权重 / ONNX / engine 体积、主机内存和峰值 / 稳态显存。至少交付一份精度—延迟—内存取舍表及配置选择理由，不要求所有候选均胜过基线。完整 INT8 实验转入 P1.Q，**P0 的配置评估不依赖 INT8 成功**。

#### 3.3 可靠异步 SDK、缓冲复用与 GPU 并发

异步接口优先沿用拥有型任务和 future，支持多调用方提交；同步接口复用同一执行路径。先完成 1 槽位可靠基线，再完成 2 槽位隔离与比较，默认部署使用实测更合适的配置，不扩张到任意规模调度器。

```text
本地 SDK / CLI / TCP / 定时图像请求回放
                  ↓ 拥有型输入 + request_id
             有界 FIFO → 1～2 个 GPU 槽位 → 数据就绪的拥有型结果
                  ↓                              ↓
          明确接纳 / 拒绝统计             future / TCP 交付与延迟统计
```

- **请求语义**：FIFO 指待执行任务的出队顺序；2 槽位不保证完成顺序，按 request_id 关联结果。队列满时明确拒绝；已接纳任务得到结果或明确错误，正常关闭采用 drain。P0 不静默淘汰旧请求，最新帧模式单列 P1.F。
- **槽位隔离**：每个同时在途槽位独立持有执行上下文、Stream / Event、设备输入输出及所需 scratch；完整 GPU 路径还持有原图 RGB8 设备缓冲和所需 Pinned Memory。共享只读引擎等对象的条件按实际 API 验证。GPU 槽位数、CPU Worker 数和连接数分别配置。
- **完成与复用**：预分配并复用缓冲，H2D → GPU 预处理（启用时）→ TensorRT → D2H → 主机读取遵守依赖；同一槽位优先使用同一 Stream，跨 Stream 时以 Event 明确衔接。future 完成代表约定结果已经可用。槽位可复用之前，结果应进入独立拥有的存储，或继续持有受限缓冲租约；输入、Pinned Memory 和输出不得被异步操作提前释放或覆盖。
- **资源上限**：队列、GPU 在途任务、待交付结果分别限制数量和字节；接纳前预留结果额度。慢消费者或慢读不能导致内部完成队列无界增长。调用方取走结果后的长期存储单独归其负责，不混同运行时预算。
- **错误与关闭**：覆盖超时、断连、非法输入、慢消费者、关闭与提交竞争。调用方停止等待不代表 GPU 工作已取消；在安全完成前继续持有资源。停止接纳后排空已接纳任务，等待设备安全完成再释放资源；设备致命错误允许显式失败并重启。

分别记账权重、上下文工作内存、设备缓冲、Pinned Memory、预处理和结果缓存。原图 RGB8 上传缓冲按支持的最大边长 / 像素数及槽位数设容量和预算，遵守现有输入上限与乘法溢出校验；原图缓冲不能按 518×518 固定输入大小估算。配置预算与进程实测总内存分开；TensorRT builder workspace 限额不能当作运行时显存总上限。比较 1 / 2 槽位的 P99、吞吐、显存和真实重叠，双槽位无收益也应保留正确性与测量证据。

#### 3.4 完整 GPU 融合预处理与实际链路对照

**V2.4 P0 实现完整 GPU 预处理：上传已解码 RGB8，在 GPU 完成除以 255、双线性缩放、补边、通道归一化及 HWC→NCHW，直接写入 TensorRT 输入缓冲区。** 保留 CPU 黄金参考与局部 GPU 路径做消融对照；完整 GPU 路径必须实现、集成和验收，最终部署选用哪条路径由端到端实测决定。本次范围取代旧版“默认只迁移归一化与布局、其余留在 CPU”的限制。

**CPU / GPU 分工与执行链路：**

```text
CPU：接收 / 校验 RGB8，计算缩放和补边元数据，预留资源并调度
    ↓ H2D：原始 RGB8（图像文件需要解码时，解码由入口完成）
GPU：除以 255 + 双线性缩放 + 补边 + 归一化 + HWC→NCHW
    ↓ 直接写入同一槽位的 TensorRT 输入缓冲
GPU：TensorRT 模型推理 → D2H
CPU：等待结果可读，裁除补边、恢复原图尺寸，交付拥有型结果
```

基础实现先保证每个目标像素 / 通道正确，再实现有依据的融合或访存改进。融合 kernel 根据目标坐标判断补边；有效区域反推原图采样位置，读取四个相邻源像素，按参考顺序转换数值并插值，随后归一化并写入 NCHW。补边区域直接产生对应的归一化值，不要求生成原图 FP32、完整缩放图、补边图等多份中间数组。kernel 的线程分工及访存选择用测量解释，不预填加速结论。

**必须保留的数值和接口契约：**

- 几何规则沿用 CPU 参考：等比缩放尺寸的整数取整、half-pixel 坐标、边界 clamp、居中 padding 与奇数余量落在右 / 下；同一份几何元数据继续用于 CPU 后处理。
- 当前参考先将 RGB8 转 FP32 并除以 255，再进行双线性插值；GPU 基础实现沿用此顺序。融合或 FMA 带来的浮点差异按预先冻结的容差验证，不把“先插值再除以 255”在数学上的等价当作逐位一致。[CUDA 浮点计算说明](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#floating-point-math-is-not-associative)
- RGB 通道均值为 `{0.485, 0.456, 0.406}`，标准差为 `{0.229, 0.224, 0.225}`。补边先取 RGB 零值，再归一化为 `-mean / std`，不能将最终 NCHW 补边区域直接填零。
- 输出布局、尺寸和类型必须与 engine 绑定一致。现有 FP32 / 混合 FP16 engine 的输入输出均为 FP32，不能因模型内部使用 FP16 就改写 half 输入；类型契约若另行变更须独立验收。
- 当前 `run_raw(PreparedImage)` 入口接收主机张量并执行上传；完整 GPU 路径需增加内部衔接，直接使用 kernel 写好的设备输入，避免重复 CPU 预处理、回传中间张量或再次上传。保持对外 RGB8 / 拥有型深度结果接口，设备缓冲由槽位内部管理。

**对照实验：**

| 路径 | CPU 像素处理 | 上传数据 | GPU 预处理 |
|---|---|---|---|
| A：现有 CPU 基线 | 除以 255、缩放、补边、归一化、转 NCHW | FP32 NCHW 模型输入 | 无 |
| B：局部 GPU 对照 | 除以 255、缩放、补边 | FP32 HWC 模型尺寸图像 | 归一化 + HWC→NCHW |
| C：完整 GPU 候选 | 无；CPU 仅准备元数据与调度 | 原图 RGB8 | 除以 255、缩放、补边、归一化、HWC→NCHW |

A 为现有实现；B、C 为待实施对照，不作为已有能力描述。B 将现有融合循环中的补边拆出时，新产生的主机数组与拷贝也必须计入成本。三条路径使用相同模型、精度、数据、Worker / 槽位数和到达率；先固定一套模型配置比较路径，再对最终选择的模型 / 精度组合复验，避免无依据扩张实验矩阵。

正确性覆盖 518 / 392 静态模型配置、横图 / 竖图、奇数补边、无需缩放、边界采样、单像素等已支持的极端尺寸、非整块尾部与极端颜色。逐层比较预处理张量、模型原始输出、还原结果及任务指标；非法尺寸按输入契约拒绝。保留 CUDA 内存 / 同步检查与多槽位结果关联、错误和关闭回归，kernel 边界测试不要求模型支持动态 shape。

设备微基准比较完整 GPU 路径的基础 / 优化实现，使用 CUDA Event 并记录形状、预热和重复次数。端到端对照包含 CPU 预处理、主机暂存拷贝、H2D 字节数与耗时、GPU 预处理、模型、D2H、CPU 后处理、分配和同步；分别测单请求与持续并发下的 P50 / P95 / P99、吞吐、失败 / 拒绝及 CPU / 内存 / 显存占用。Nsight Systems 解释 CPU 与 GPU 工作重叠、GPU 预处理与模型的资源竞争，Nsight Compute 只分析目标 kernel。采集限制在 V2.1 核验；受限指标说明缺失，并保留可验证的时间线、设备计时与原因分析。[NVIDIA 性能测量](https://docs.nvidia.com/deeplearning/tensorrt/latest/performance/benchmarking.html)

验收要求完整 GPU 路径的实现、集成、正确性及三路径对照证据齐全，**不预设整模型必须加速**。若 C 更慢，允许最终部署选择 A 或 B，并记录输入尺寸、并发与资源条件下的原因；完整负向实验可通过本项，未实现或未通过正确性验收不能标记完成。仅有独立 LayerNorm / GEMM 微基准不能替代本项。

#### 3.5 性能、过载与长稳验收

| P0 实验 | 固定条件 / 改变变量 | 必须输出 |
|---|---|---|
| 精度与配置 | 同硬件、数据与计时口径，分别改变输入尺寸、FP32 / FP16 | 任务效果、延迟、内存与工件体积；最终配置依据 |
| 缓冲与并发 | 同模型 / 精度 / 到达率，分别比较分配复用、1 / 2 槽位 | 阶段时延、P99、吞吐、显存、隔离正确性与真实重叠 |
| CUDA 集成 | 固定模型 / 精度 / Worker / 槽位与到达率，比较 A CPU、B 局部 GPU、C 完整 GPU；C 再比较基础 / 优化实现 | 张量与全模型精度、上传量、分段 / 端到端耗时、吞吐 / P99、资源占用与 Profiler 解释 |
| 背压与稳定性 | 正常、饱和、持续过载、慢消费者、错误与关闭回归；预热后至少 30 分钟长稳 | 接纳 / 拒绝 / 失败 / 交付计数、输出抽检、内存趋势、延迟波动与安全回收证据 |

主要配置至少 3 次独立重复，记录样本量、供电、温度、频率 / 后台负载及运行环境。Profile 与正常计时分开采集；CPU Sanitizer / TSan 和 CUDA 检查分别覆盖对应问题。长稳测试只说明本次条件下的表现，不自动构成生产可靠性证明。

本地时延从约定输入入口到完整结果可用，排队、CPU 前处理 / 暂存拷贝、H2D、GPU 前处理、模型计算、D2H 和 CPU 后处理分别记录。A / B / C 主对照统一从已解码 RGB8 输入计时；需要文件解码的入口另测含解码全链路，不能只为某一路排除解码。TCP 由客户端单调时钟测发送前到完整响应解析，不能跨机器相减时间戳。GPU 时长与主机端到端口径分开，重叠阶段不直接相加；成功样本 P99 与拒绝 / 失败率并列，样本不足时说明估计限制。

输入、接纳、执行完成、交付和错误分别记账，统计口径及终态可核对；运行中计数包含排队 / 在途，drain 后可验证终态守恒。错误和关闭测试针对真实风险，不因增加配置而机械复制测试数量。

### 4. P1 选做：按岗位与瓶颈每次先选一个分支

以下内容均保留在路线中，**未实施不影响 V1 / V2 P0 完成**。优先完成主线，再根据目标岗位或 Profile 选择分支；不同时启动多条进阶路线。

| 编号 | 选做内容 | 选择条件与独立验收 |
|---|---|---|
| P1.Q | INT8 PTQ、显式 ONNX Q/DQ、敏感层分析 | 投递量化 / 部署优化岗位时优先；真实 INT8 执行覆盖、精度与性能对照完整 |
| P1.F | 录制视频 / 摄像头入口、最新帧策略与结果时效 | 需要连续视频集成时选择；解码成本、丢弃终态、结果年龄与发布顺序明确 |
| P1.N | epoll LT / eventfd 与网络背压 | 网络成为瓶颈或目标 JD 强调网络时选择；I/O 不等待推理、有界完成通知、连接代次与关闭正确 |
| P1.K | 独立 LayerNorm 或 GEMM；按需接入 TensorRT Plugin | 面向算子 / 引擎岗位或存在真实热点、不支持节点；参考实现、性能对照齐全，Plugin 另做图内与整模型回归 |
| P1.R | ROS2 薄适配，或控制任务资源干扰实验 | 对应机器人集成职责时选择；组件隔离、接口 / 时间戳和开销可复验，不扩成整机系统 |

#### 4.1 P1.Q 的量化验收

1. 校准、调参和最终测试按场景 / 视频序列隔离，保存代表性样本清单、预处理和随机种子；最终测试集不参与尺度选择。
2. 按锁定版本选择兼容 PTQ 工具，优先显式 ONNX Q/DQ（例如适用的 NVIDIA Model Optimizer 流程），保存尺度、节点范围及工件。仅设置 INT8 flag 不算完成。[NVIDIA 量化工作流](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/quantized-types-workflows.html)
3. 从支持的 Linear / MatMul 等节点开始，分析中间输出和任务退化；敏感层可保留浮点精度。记录选择性量化范围，不盲目全图量化。[TensorRT 精度与性能取舍](https://docs.nvidia.com/deeplearning/tensorrt/latest/performance/optimization.html)
4. 从构建日志、层信息 / 实际 kernel 确认目标节点真正执行 INT8，并记录转换开销；与同尺寸 FP16 对比任务指标、延迟和内存。全部回退浮点需标为未实现 INT8 执行。
5. 精度超限或性能退化时记录原因及一次有针对性的调整，允许最终部署选择 FP16。真实量化执行与完整负向结论可通过实验验收；只有导出文件、失败日志或兼容性调研不能标为 P1.Q 实作完成。

FP16 与 INT8 容差分别定义；校准规模用覆盖与稳定性说明。工具链受阻时如实标记该分支未完成，不牵连已通过的 P0，也不自动扩项到 QAT、剪枝或蒸馏。

#### 4.2 P1.F 的实时帧验收

可靠请求模式仍为默认，实时帧模式必须显式选择。只淘汰尚未执行的旧帧；替换、超期和晚到结果都有终态与计数。GPU 在途任务不可假定能立即取消，其资源等待安全完成；用帧序号处理乱序，旧结果不得覆盖已发布的新结果。

回放计划释放、实际释放与结果可用采用同一时钟域，分别报告生成器滞后、结果年龄、有效 FPS 与时效达标率；回放时间戳不能写成真实传感器采集时间。明确有效 FPS 的统计窗口、正确且按时交付条件，丢弃 / 失败与迟到结果单列。解码成本先单列，再测包含解码的完整入口。

P1.N 若实施，仍需有界完成队列 / eventfd、连接标识与代次防止 fd 复用误投递、慢读背压及安全关闭。独立 LayerNorm 对照 PyTorch，GEMM 对照 cuBLAS；Plugin 需额外验证格式 / 精度和图内替换。选做不降低正确性要求。

### 5. E1 设备分支：真实平台到位后独立验收

E1 当前未实施，也不是主线前置条件。有实际设备后只选一个平台；选择依据为目标岗位、设备与可复用后端，复用 TensorRT 时可考虑 Jetson，其他 ARM / NPU 则围绕对应 SDK 单独适配。桌面 engine 或兼容模式不能直接证明 JetPack / DriveOS 可用。

验收包括目标架构构建、目标版本导出 / 引擎重建、算子与精度适配、启动和错误处理，以及同样例回归；再在记录的功耗模式、时钟与散热条件下测持续 Batch=1 P99、有效吞吐、RAM、温度、频率及功率。Jetson 可按实际平台用 tegrastats，功率必须说明传感器 / 功率轨口径，GPU 功率不能冒充整机功率。[Jetson 监测工具](https://docs.nvidia.com/jetson/archives/r36.5/DeveloperGuide/AT/JetsonLinuxDevelopmentTools/TegrastatsUtility.html)

没有设备时可整理迁移清单、模型包与重建流程，真实板端延迟、功耗、热稳态和机器人闭环均标“未验证”。不要求采购开发板，也不提前加入 DLA、BSP / 驱动、RTOS、安全认证或实车集成。

| V2.3 可靠异步运行 | 拥有型异步 SDK、FIFO / 背压、缓冲复用、1 / 2 槽位隔离；为 V2.4 明确原图上传缓冲预算与依赖 | 结果就绪语义、关联与资源上限正确；比较吞吐 / P99 / 显存，不要求双槽位更快 |
| V2.4 完整 GPU 预处理 | RGB8 上传；GPU 融合除以 255、缩放、补边、归一化及 HWC→NCHW，直接连接 TRT 输入；保留 A / B 对照 | C 基础 / 优化实现、三路径正确性与端到端 / Profiler 对照、资源与设备检查齐全；无收益可形成完整结论，未实现 C 不算完成 |

V2.4 内部按以下顺序推进，每一步先满足对应停止条件：

1. **冻结对照与契约**：保存 A 的黄金张量、几何元数据、任务结果和基线；确认 RGB8 上限、FP32 I/O、容差、代表性尺寸与计时入口。
2. **建立 B 局部对照**：实现并接入归一化 / 布局 CUDA 路径，核对与 A 一致，计入拆分补边带来的中间数组和拷贝。
3. **实现 C 基础路径**：为每个槽位准备有界 RGB8 上传缓冲和依赖，完成完整 GPU 像素处理并直接写入 TRT 输入；张量与全模型验收通过后再优化。
4. **融合与测量**：完成有依据的融合 / 访存改进，做基础 / 优化 kernel 对照及 A / B / C 单请求、持续并发实验；只对必要配置重复测量。
5. **集成验收与交付**：完成设备检查、资源复用、错误 / 关闭及必要的 1 / 2 槽位回归，输出路径选择理由、未解决限制和复现命令。后续 V2.5 / V2.6 在最终组合上完成长稳与交付；不因 C 无加速而继续无边界调优。

- **选择 P1**：写明分支编号、对应岗位 / 瓶颈、所需工件与停止条件，再单独实施。量化选 P1.Q，连续视觉应用选 P1.F，网络侧选 P1.N，算子侧选 P1.K，机器人适配选 P1.R；每次先做一个。
