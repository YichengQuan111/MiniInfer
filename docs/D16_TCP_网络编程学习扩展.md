# D16 原生 TCP 网络编程与推理服务

日期：2026-10-11。状态：D16.1–D16.5 已按顺序实现并验收。逐阶段日志、最终安全检查及运行命令见 [README 的 D16 记录](../README.md#d16-验收记录)，真实测量见 [基准报告](benchmark.md)。编号不代表一天完成；下文保留实施顺序及现行协议契约。

目标是从 socket / TCP 入门，逐步完成一个可测试的 C++ 推理客户端与服务端：正确传输请求，复用现有 CPU MLP，限制连接与排队资源，并处理断连、过载和关闭。按下面五个子任务依次实施，每项通过验收后再进入下一项。

## 1. 范围与复用边界

- 沿用 Linux / WSL2、C++17、CMake / CTest；使用原生 socket API 和标准库，不增加第三方网络框架。
- 客户端和服务端先都在 WSL 内运行，默认监听 `127.0.0.1`。Windows 到 WSL、局域网访问作为后续独立实验。
- 固定 `64 → 128 → 10` CPU MLP，Batch 为 1–256；参考输入已归一化，客户端不再除以 16。
- 服务启动时加载一次模型，连接处理层调用现有 `Runtime::run()`；推理 Worker 不处理 socket 收发。
- 先完成单连接请求响应，再增加固定数量的连接处理线程。最终支持连接复用，每连接最多一个在处理的请求，不增加请求流水线、乱序响应或自动重试。
- epoll / Reactor 留作 V2 的 P1 进阶项；HTTP/gRPC、TLS、鉴权、服务发现、分布式调度和 GPU 不进入 D16 验收。

原规范中排除网络的条款仅约束 D1–D15 基础范围；D16 允许本文列出的 TCP 扩展。当前状态及后续版本见 [主规范](<../MiniInfer 项目说明与 AI Agent 开发规范.md>)、[V1 / V2 策略](MiniInfer_V1_V2_求职改进策略.md)。

## 3. D16 消息协议

TCP 提供字节流，应用不能依赖一次发送对应一次接收。长度字段用于确定消息边界，接收端必须允许帧头或消息体分多次到达，也必须正确处理连续到达的多个帧。[TCP 规范](https://www.rfc-editor.org/rfc/rfc9293.html)

### 3.1 固定帧头

每帧由 16 字节帧头和 `body_bytes` 字节消息体组成。以下为已实现契约；需要调整时同步更新编码器、解码器和测试。

| 字段 | 字节数 | 约定 |
|---|---:|---|
| magic | 4 | 固定字节 `MINI` |
| version | 2 | 协议版本 1 |
| type | 2 | 请求：1 为 Echo，2 为 MLP 推理；响应为对应请求类型按位或 `0x8000` |
| request_id | 4 | 客户端在连接内递增，响应原样携带；用于匹配与日志，不提供重试去重保证 |
| body_bytes | 4 | 消息体字节数，不包含帧头 |

整数统一使用大端网络字节序。逐字段编码，不直接发送 C++ 结构体，也不以未对齐指针转换读取网络字节。FP32 使用 IEEE 754 的 32 位位模式，经 `memcpy` 与 `uint32_t` 转换后按大端编码；平台条件不满足时明确拒绝启动。磁盘 `.f32` 仍是既有的 little-endian 格式，由客户端加载后转换。

### 3.2 请求与响应

- Echo 请求体是最多 1024 字节的原始数据；成功响应体为 `status` 后跟原样数据。
- MLP 请求体为 `batch:uint32`，随后是行主序的 `batch*64` 个 FP32；长度必须精确等于 `4 + batch*64*4`。
- MLP 成功响应体为 `status:uint32`、`batch:uint32`、`batch*10` 个 FP32 logits、`batch` 个 uint32 labels。labels 必须为 0–9；长度为 `8 + batch*44`。
- 所有响应体以 `status:uint32` 开始：0 成功，1 `BAD_REQUEST`，2 `BUSY`，3 `SHUTTING_DOWN`，4 `INFERENCE_FAILED`。错误体随后可带最多 1024 字节 UTF-8 说明，客户端依据状态码判断。
- 请求与响应都校验版本、类型、长度与 request_id。未知版本、未知类型和损坏帧不能继续按正常数据解释。

MLP 请求体上限为 `4 + 256*64*4 = 65540` 字节；包含帧头为 65556 字节。全局先按此上限拒绝异常长度，再检查消息类型对应的精确长度和 Batch。所有乘法检查溢出，分配前验证上限，构造 `MlpInput` 时继续检查 NaN / Inf。成功响应体在 Batch=256 时为 11272 字节。

损坏帧头、超限长度或半帧 EOF 直接结束连接，不为消费非法消息体无限等待。完整且可信的请求出现参数错误时，限时返回 `BAD_REQUEST` 后关闭连接；完整合法请求遇到 `QueueFull` 返回 `BUSY`，计算异常返回 `INFERENCE_FAILED`，连接仍可用于下一次请求。关闭期间返回 `SHUTTING_DOWN` 后关闭；已无法通信时只记录失败并回收。

### 3.3 收发与时间限制

`send_all` / `recv_exact` 返回或报告可区分的成功、干净 EOF、截断帧、超时和系统错误。处理 `EINTR`；非阻塞收发遇到 `EAGAIN/EWOULDBLOCK` 时等待就绪并重算剩余时间。读完整帧和写完整帧分别使用 `steady_clock` 绝对截止时间，零星到达的字节不能无限延长整个操作。连接等待下一帧也有空闲期限。

收到完整请求后对端关闭写方向，仍可尝试发送该请求的响应；EOF 不表示已提交的推理被取消。发送使用 `MSG_NOSIGNAL` 并处理失败，避免客户端断连导致整个进程因 `SIGPIPE` 退出。[recv 文档](https://man7.org/linux/man-pages/man2/recv.2.html)、[send 文档](https://man7.org/linux/man-pages/man2/send.2.html)

## 4. 线程与资源所有权

```text
infer_client
    ↔ TCP 帧
连接处理线程：收完整帧 → 校验/解码 → Runtime::run → 编码/发送
    → Runtime 有界等待队列 → 推理 Worker → 独立 MlpResult
```

- `UniqueFd` 唯一拥有监听或连接 fd，移动后源对象失效；不得复制所有权或用 `detach()` 回避回收。
- 接入线程将连接所有权移交给有界的连接处理层。可以使用独立的 ThreadPool，但不能把 socket 收发提交给 Runtime 的推理池后再等待同池任务。
- 初始可配置 4 个连接处理线程、8 个等待连接；等待连接有排队期限，出队先检查是否过期。接入层满时立即关闭新连接，此时尚无完整请求，不承诺返回业务错误码。已接收的完整推理请求遇到计算队列满才返回 `BUSY`。
- 连接层同时限制接入数、等待连接数、单帧字节数和响应大小；Runtime 的 `queue_capacity` 只限制等待计算的任务，不替代这些上限。
- 每个处理线程串行处理该连接的请求，拥有接收和发送存储；`MlpInput` 拥有解码后的数值，`MlpResult` 在编码完成前保持存活。每连接至多一个请求占用推理或回包资源。
- 输入提交成功是“Runtime 已接受”的边界。客户端超时或断连后，已提交任务仍执行到安全完成，再回收结果；D16 不增加计算取消或强行终止 Worker。

关闭按以下顺序推进：停止接入和新的业务提交，唤醒等待连接；让收发通过停止通知或截止时间退出；对已经提交的推理执行 Runtime drain；仍可通信的连接限时回包；join 连接线程，最后销毁 Runtime 及其资源。信号处理只通知退出，不能在异步信号处理函数中调用带锁的 Runtime shutdown 或 join。收发有期限不等于计算排空有硬性时间保证。

## 5. 测试与完成定义

| 测试组 | 必须覆盖的证据 |
|---|---|
| 编解码 | 固定字节样例；逐字节喂入；多帧拼接；错误 magic / version / type / 长度 / Batch；NaN / Inf；整数溢出与分配上限 |
| 收发 | 用受控 I/O 或测试替身稳定制造短读、短写、EINTR、EAGAIN、EOF、超时；半关闭和复位连接有对应处理 |
| 真实 TCP | 回环地址、系统分配端口；服务就绪通知后再连接；参考 Batch 的 labels 一致，logits 满足原 `atol=rtol=1e-4`；256 行由参考数据重复构造 |
| 并发与过载 | 多客户端混合 Batch；连接数与等待队列有界；用 gate 控制测试执行器的完成，在 `workers=1, queue_capacity=1` 等小配置下稳定触发 BUSY；失败后仍可处理合法请求 |
| 生命周期 | 空闲连接、半帧、慢读、推理中断连、关闭竞争；反复启动/连接/退出后 fd 与线程回收；已接受计算恰好完成一次 |
| 回归与检查 | Debug / Release 原有测试和新增测试；ASan+UBSan；相关并发用例单独 TSan，环境限制如实记录 |

协议拆分测试不依赖 TCP 恰好怎样分包；仅靠多次 `send` 或 `sleep` 不能证明接收会按指定片段返回。真实 TCP 集成测试与可控 I/O 单元测试分别承担连通性和边界验证。测试必须设置整体超时，并在失败路径回收子进程、fd 和线程；单用 `socketpair` 不能替代真实 TCP 回环验收。

小规模 Release 测量分别保存进程内 Runtime 与 TCP 客户端结果，固定模型、Batch、Worker、并发数、连接复用策略和请求序列。客户端用自己的单调时钟测量从发送前到完整响应解析后的耗时；建连耗时单列。记录成功、业务拒绝、协议/连接错误、超时及 P50/P95/P99；发送成功不等于客户端已收到结果，不能用服务端发送数代替客户端成功数。D16 不要求性能提升，V2 再开展系统负载与优化实验。

## 7. 与 V1 和 V2 的衔接

本节于 2026-10-15 同步完整 GPU 预处理规划；前文 D16 的验收与测量保留原时点记录，当前版本进度以 README 及对应验收记录为准。

V1 以 C++ 部署 SDK 和模型包为主交付，复用 D16 的连接、帧边界、错误处理与回归方法作为 TCP 入口；Depth Anything V2 Small 新增 RGB 请求和 FP32 相对深度响应，先完成 Python / ORT / TensorRT 精度对照，再以单 GPU 槽位接入。不能把图像塞进 MLP 的 64 维请求，稠密结果需要独立响应上限与全局字节预算。

V2 P0 聚焦两种静态尺寸 / FP32 / FP16 选择、可靠异步 SDK、GPU 缓冲复用与 1 / 2 槽位、完整 GPU 融合预处理及性能 / 过载 / 长稳验收。V2.4 计划将已解码 RGB8 上传，由 GPU 完成除以 255、双线性缩放、补边、归一化和 HWC→NCHW 并直接写入 TRT 输入；CPU 保留校验、几何元数据、调度与结果后处理。保留 A CPU、B 局部 GPU、C 完整 GPU 三路径对照；C 必须实现并验收，默认路径按实测选择，新增方案仍待实施。

预处理迁移改变服务端内部执行位置，沿用 RGB8 请求 / FP32 深度响应契约，不要求客户端先归一化。每槽原图上传缓冲、所需 Pinned Memory 及在途资源纳入字节预算；H2D → GPU 预处理 → TRT → D2H → CPU 后处理完成后才交付拥有型结果，不能把 GPU 提交当作响应已就绪。可靠 TCP 请求保持明确接纳 / 拒绝和终态，慢读与断连不提前释放设备仍在使用的资源。

INT8 PTQ、实时帧策略、epoll / eventfd、独立 LayerNorm / GEMM、Plugin 等为 P1，不阻塞主线；实时帧策略不能用于静默丢弃可靠请求。若实施网络重构，再单独验收连接代次、迟到结果、背压和关闭。真实端侧硬件留待 E1。

后续只需按实现需要新增消息类型；更改已有字段语义或布局时升级协议版本。D16 的 MLP 客户端与回环测试保留为网络和计算回归。主题“MiniInfer：C++ 视觉模型部署与推理性能优化”的必做 / 选做任务、缩减顺序和验收见 [V1 / V2 策略](MiniInfer_V1_V2_求职改进策略.md)。
