## 2. v0.1 的目标与完成标准

**目标：用 C++17 在 Linux 上构建一个 CPU-only 的固定 MLP 推理运行时，并提供正确性、资源安全、并发可靠性和可复现测量的证据。**

这个项目同时有两层价值：功能上能从真实权重完成分类；工程上能解释数据由谁拥有、请求如何执行、错误如何返回，以及性能数字如何得到。后者决定作品集的说服力。

| 必达目标（P0） | 最终应交付什么 | 如何判定完成 |
|---|---|---|
| 可构建、可测试 | C++17 工程、CMake、CTest | 相近 Linux 环境可以按命令构建，核心测试实际执行并通过 |
| 数值正确 | 模型导出脚本、权重加载、Linear / ReLU / Argmax、同步推理、infer_cli | 手算算子用例通过；完整推理与导出的 FP32 参考 logits 在有依据的容差内一致，类别一致 |
| 生命周期明确 | Buffer、TensorView、只读 Model、Worker 私有 Workspace、拥有数据的 Input / Result | 移动、边界、错误路径有测试；ASan / UBSan 结果可追溯 |
| 并发行为明确 | 有界队列、固定 Worker 池、future、drain shutdown | 1/2/4 Worker 结果正确；满队列拒绝、任务异常、关闭及重复关闭有测试；环境支持时独立运行 TSan |

原文档按 15 天、每天约 1.5–2 小时规划，折合约 22.5–30 小时。这是安排依据，尚未由实际开发记录验证；完成应按证据判断，不能按天数推定。

v0.1 范围固定为 CPU、FP32、连续内存和两层 MLP。ONNX 图解析、CUDA / TensorRT、网络服务、量化、手写 SIMD、无锁队列及通用插件系统均不进入本轮验收。

## 3. 固定模型为什么是合适的验证载体

采用 digits 的 8×8 图像，将 64 个像素按 `pixel / 16.0` 预处理。计算路径固定：

```text
输入 X [B,64]
  → Linear：X × W1ᵀ + b1，W1 [128,64]，b1 [128]
  → ReLU：[B,128]
  → Linear：A1 × W2ᵀ + b2，W2 [10,128]，b2 [10]
  → logits [B,10] → 按行 argmax → labels [B]
```

固定网络能覆盖张量布局、权重加载、中间内存、算子组合和并发执行，又能控制调试范围。没有图解析和动态调度之后，数值错误更容易归因到布局、预处理或计算实现。

Python 负责离线训练、导出与生成参考答案；C++ 负责加载和推理。参考 logits 必须用**导出后的 FP32 权重**重新计算，这样验证的是同一组数据上的实现差异。不能只比较类别：不同 logits 可能恰好给出相同 argmax。

全部采用行主序连续 FP32；scikit-learn 的 `[in,out]` 权重导出时转为 `[out,in]`。裸 `.f32` 文件简单，但没有自描述形状，因此加载器必须按固定契约精确检查字节数和读取结果。网络结构、布局、预处理和参考答案共同构成一份契约，任何一项变化都会影响验证。

这个网络的计算量小，适合证明正确性。其线程调度、复制和分配成本可能影响整体性能，具体占比必须实测；不能由这个例子推断大模型或 GPU 的性能。

## 4. 技术栈的底层逻辑

技术栈围绕一条链路选择：**明确数据契约 → 控制资源生命周期 → 正确执行 → 安全调度 → 用证据验证与测量。**

| 技术选择 | 为什么选它 | 对实现的直接要求 |
|---|---|---|
| C++17 + 标准库 | 可以直接表达内存所有权、移动、线程同步和异步结果，训练本项目要展示的系统能力 | 用 RAII 保证正常路径和异常路径都释放资源；避免引入不必要的语言版本与库依赖 |
| Linux x86_64；Windows 开发时可用 WSL2 | 提供目标构建与调试环境，便于记录进程、内存和性能信息 | 实施前核验实际环境；WSL 的工具限制和环境差异需记录，测量结论只适用于实测环境 |
| GCC / Clang、CMake、CTest | 将构建和测试变为可重复的工程流程，降低手工运行遗漏 | 开启规定警告；注册并实际执行测试；Debug、安全检查构建和 Release 计时分开 |
| Python + NumPy + scikit-learn | 用较少准备工作获得真实模型与可追溯参考数据，将训练与 Runtime 开发分开 | 固定种子、数据划分、参数和版本；C++ 运行时不依赖 Python |
| 标量 FP32 算子 | 计算路径易解释，能建立之后所有优化的正确性基线 | 先覆盖小矩阵、非方阵、多 Batch 和非法形状，再组合完整推理 |
| Buffer / TensorView / Workspace | 将“拥有内存”“描述数据”“管理临时空间”分开 | Buffer 独占且可移动；View 不延长寿命；每个 Worker 的临时空间互不共享写入 |
| 有界队列 + 固定 Worker + mutex / condition_variable | 使积压数量和执行资源可配置，便于明确同步与关闭行为 | 满队列立即拒绝；请求拥有输入；Model 只读共享；future 传递结果和任务异常；关闭后 drain 并 join |
| GDB、ASan / UBSan、独立 TSan | 分别支持故障定位、内存/未定义行为检查与数据竞争检查 | 与功能测试结合；检查通过仅覆盖实际运行的路径，不能当作所有错误不存在的证明 |
| steady_clock、Release 基准、可用时 perf | 用稳定的耗时口径测量，再根据实际热点判断优化方向 | 预热、重复、固定负载；分别统计排队、执行和端到端耗时；不能把拒绝请求计入成功吞吐 |

### 所有权如何支撑并发

权重加载一次后只读共享，避免每个 Worker 复制模型；中间计算写入 Worker 私有 Workspace，避免请求相互覆盖；提交的 Input 和交付的 Result 各自拥有数据，避免调用者提前释放内存。TensorView 只在这些拥有者存活期间借用数据。

这使算子层只需关心数学计算，执行器关心计算组合与临时空间，Runtime 关心请求调度和生命周期。模块划分的意义是让责任可以分别验证，而非增加类的数量。

有界队列只限制等待中的请求数量。要估计内存上限，还要考虑单请求 Batch、正在执行的请求、Workspace，以及调用者保留的结果；仅设置队列容量不能声称系统总内存有固定上限。

### 为什么先同步，再并发，再优化

同步推理对齐参考结果后，它就成为异步路径的基线。随后出现的问题可以重点检查输入寿命、Workspace 隔离、同步协议和关闭流程。若一开始混合算法、线程和优化，故障来源难以区分。

同步基线也提供性能对照：增加 Worker 后，是否提高吞吐、是否增加排队或尾延迟、是否增加内存，都需要同条件比较。性能结论来自测量，不能由线程数量直接推出。

### 为未来 GPU 留下什么

保留 Input / Result、Model、执行器、调度层之间的清晰责任边界，CPU 算子实现集中于 CpuExecutor。后续版本可以根据实际模型增加执行适配；当前只需把边界做清楚。

TensorView 当前仅表示主机可访问内存。未来设备内存、拷贝、Stream / Event 和 GPU 完成语义需要自己的契约，不能把 GPU 地址当作可直接解引用的 CPU 指针。V1 / V2 策略仍是后续工作，不能进入 v0.1 的功能清单。

## 5. 进入 S（策略）前需要定下的事项

以下是从现有契约推导出的实现决策点，原文档尚未给出完整答案；应在对应任务开始前确定并记录。

| 决策点 | 为什么影响后续工作 |
|---|---|
| 实际 Linux / WSL 环境和唯一开发目录 | 决定构建、Sanitizer、perf 是否可用，避免 Windows 与 Linux 副本出现代码或数据差异 |
| 最大 Batch 或安全尺寸策略、Workspace 容量策略 | 决定输入验证、溢出检查及临时空间占用；需要区分基础复用与额外优化实验 |
| 同步 `run()` 的 Workspace 与线程安全语义 | Worker 私有 Workspace 解决异步路径，但同步调用也必须明确使用什么资源、是否允许并发，以及关闭后的行为 |
| 队列容量含义与拒绝错误的交付方式 | 应明确等待任务计数；队列满/已关闭是立即抛出还是返回状态，Worker 执行异常则由对应 future 传回 |
| 关闭调用的并发约束 | 除重复关闭安全外，还要确定 submit 与 shutdown 竞争时的接受边界，以及多个调用者能否同时关闭 |
| 参考数据清单与测量口径 | 固定参考样本、容差依据、argmax 并列规则；定义计时点、成功/拒绝/失败计数、内存指标的采集方式 |

下一阶段 S 应按原规范收敛为三个依赖阶段：同步正确性闭环（D1–D7）、基线与并发可靠性（D8–D12）、测量与可复现交付（D13–D15）。保留 D6、D10、D12、D15 检查点，进度不足先舍弃 P1。O 阶段再逐项实施，每项完成后用构建、测试或实测证据验收。
